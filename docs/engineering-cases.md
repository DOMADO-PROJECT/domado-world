## 측정 기준

짧은 커밋 해시는 비공개 구현 저장소의 내부 식별자입니다.<br/>
성능 값은 측정 시점과 조건에 따라 세 기준으로 나눴습니다.

- **전후 실측:** 같은 조건에서 수정 전·후 빌드를 비교
- **과거 빌드 재측정:** 변경 전·후 리비전을 같은 조건으로 다시 빌드해 비교
- **정적 확인:** Git blob, 파일 크기, 빌드 산출물로 확인

각 수치는 해당 사례 안에서만 비교합니다.<br/>
내부 측정의 원시 결과는 이 공개 저장소에 포함하지 않았으며 재현에 필요한 조건과 남은 한계는 사례별로 적었습니다.

### 1차 — 고주사율 프레임 페이싱과 프레임별 할당

**기간:** 2026-07-13 ~ 07-14

#### 문제

초기 모바일 게임 루프는 시간 기반 skip을 사용했습니다.<br/>
일부 120Hz 구간에서는 25ms 간격이 나타났고 90/144Hz에서는 짧고 긴 간격이 번갈아 나타났습니다.<br/>
평균 FPS만 보면 목표에 가까워도 프레임 간격은 흔들렸습니다.<br/>
조이스틱 경계값, 충돌 배열과 작업 배열도 프레임마다 다시 만들어졌습니다.

RAF 호출이 누락된 뒤 skip counter가 그대로 남으면 다음 호출도 건너뛰어 지연이 한 번 더 늘 수 있었습니다.

<br />

#### 원인

기기 RAF 주기와 목표 60FPS를 단순 시간 임계값으로만 맞추면 호출 간격의 작은 오차가 쌓여 실행 간격이 번갈아 바뀝니다.<br/>
평균값보다 프레임 간격과 실행 기한을 함께 다뤄야 했습니다.

<br />

#### 변경

- 모바일 가로 게임만 기기 RAF의 정수 배수로 제한했습니다.
- 60Hz→60, 90Hz→45, 120Hz→60, 144Hz→48FPS 정책을 사용했습니다.
- stride counter에 실제 경과시간 deadline과 RAF 호출 누락 보정을 결합했습니다.
- 빠른 주사율 변화와 60Hz대 연속 호출을 구분했습니다.
- 조이스틱 bounds, 충돌 사각형과 작업 배열을 재사용했습니다.

<br />

#### 검증

- 120Hz 모바일 10초 계측: `20ms 초과 간격 22회 → 0회`
- 적용 후 최대 간격: `17.7ms`
- 60/90/120/144Hz, jitter, RAF 호출 누락, 주사율 전환 시뮬레이션

<br />

#### 해석과 한계

FPS 상승을 확인한 결과는 아닙니다.<br/>
불필요한 갱신을 제한하면서 프레임 간격을 일정하게 만들었습니다.<br/>
당시 기록에는 120Hz 모바일·10초 조건 외의 기기 모델, 브라우저 버전과 원시 trace가 남아 있지 않습니다.<br/>
실제 모바일 기기의 열·배터리 전후값도 측정하지 않았습니다.

<br />

### 2차 — 렌더·입력·오디오 핫패스

**기간:** 2026-07-14 ~ 07-16

#### 문제

- 모바일 카메라 밖 오브젝트까지 렌더링했습니다.
- 고빈도 `pointermove`마다 입력 좌표와 DOM 값을 갱신했습니다.
- 짧은 효과음을 `HTMLAudioElement` 복제로 재생했습니다.
- depth 객체와 draw closure가 반복 생성됐습니다.
- 고정 낚시꾼도 사용하지 않는 방향의 Canvas 프레임을 만들었습니다.

<br />

#### 변경

- 카메라 밖 오브젝트 렌더 제외
- pointer 입력을 RAF당 한 번으로 병합
- 짧은 SFX를 Web Audio로 디코딩하고 버퍼 재사용
- 깊이 정렬 항목을 한 번 만든 뒤 활성 배열만 재사용
- 미사용 낚시꾼 Canvas 38개 생성 제거
- 사다리 음원의 실제 사용 구간만 잘라 mono M4A로 재인코딩

<br />

#### 검증

| 항목 | 전 | 후 | 근거 종류 |
| --- | ---: | ---: | --- |
| 사다리 음원 | 9.1초 · 209,541B | 3.017초 · 25,280B | 정적 확인 |
| 미사용 낚시꾼 Canvas | 38개 | 0 | 정적 확인 |
| 844×390 touch Chromium 5초 | — | 500 RAF, 20/33ms 초과 0, Long Task 0 | 적용 후 확인 |

38개 중 `64×64` 작업 프레임 34개를 보관했습니다.<br/>
이 프레임의 원시 RGBA 픽셀만 계산하면 `557,056B`, 약 `0.53MiB`입니다.<br/>
브라우저가 실제로 사용한 메모리는 측정하지 않았습니다.

<details>
<summary>차이가 드러나지 않은 과거 빌드 재측정 보기</summary>

누락된 전후 실행값을 보완하려고 2026년 8월 25일 내부 리비전 `075f1ca`와 `6a416d4`를 모바일 가로 조건으로 다시 빌드해 각 3회 측정했습니다.<br/>
`844×390` 초기 장면의 중앙값은 두 빌드 모두 프레임당 `drawImage` 115회, RAF callback p95 0.5ms, Long Task 0회였습니다.<br/>
이 장면에서는 화면 밖 렌더 제외와 할당 재사용의 차이가 드러나지 않아 개선 근거로 쓰지 않았습니다.

</details>

### 3차 — 포트폴리오 미디어 크기와 준비 순서

**기간:** 2026-07-31

#### 문제

첫 페이지의 물결 영상은 6.18MB였습니다.<br/>
뷰어가 보인 뒤에야 영상 전송이 시작됐고 다음 페이지도 넘기는 순간 요청되어 다시 기다릴 수 있었습니다.

<br />

#### 변경

1. 이미 하던 첫 페이지 준비에 물결 영상 준비를 더해 1.2초 전환 화면 안에서 함께 처리했습니다.
2. 본문 표시 뒤 다음 페이지를 준비했습니다.
3. 나머지는 `requestIdleCallback` 또는 대체 타이머를 써서 차례로 준비했습니다.
4. 3차에서 영상을 한 차례 재인코딩했습니다.<br/>
   최종 재인코딩은 4차 초기 전달 개선에서 진행했습니다.

<br />

#### 검증

| 단계 | 내부 리비전 | 영상 크기 | 변화 |
| --- | --- | ---: | ---: |
| 3차 직전 | `78cbdd5` | 6,178,980B | — |
| 3차 완료 | `179d94d` | 2,209,111B | -64.2% |
| 4차 재인코딩 | `2328a82` | 1,378,676B | 3차 직전 대비 -77.7% |

개선 당시에는 같은 조건의 전후 로딩 시간을 저장하지 않았습니다.<br/>
두 내부 리비전을 나중에 같은 조건으로 비교했으며 과거 사용자 환경을 복원한 결과는 아닙니다.

<br />

#### 2026-08-25 과거 빌드 재측정

3차 직전 내부 리비전 `78cbdd5`와 로딩 순서 변경까지 끝난 `179d94d`의 프로덕션 빌드를 같은 조건에서 비교했습니다.<br/>
Chrome 151, `1280×720`, 모션 축소 설정 끔, 영상 전송 `400KiB/s`, 응답 지연 100ms로 고정하고 실행마다 다른 로컬 포트를 사용해 캐시를 분리했습니다.<br/>
각 빌드를 3회 측정한 중앙값입니다.

두 리비전 사이에는 영상 재인코딩과 준비 시점 변경이 함께 포함됩니다.<br/>
아래 재생 준비 시간은 두 변경을 합친 결과이며 준비 순서만의 효과로 분리하지 않습니다.

뷰어 표시는 `.portfolio-viewer`가 보인 시점, 물결 준비는 영상의 `playing` 이벤트로 `data-ready=true`가 된 시점, 전송 완료는 로컬 서버가 영상 응답을 끝낸 시점으로 정했습니다.

CDN 상태와 기기 성능이 다른 실제 사용자 환경에서는 결과가 달라질 수 있습니다.

### 4차 — 초기 번들·오디오·대형 미디어

**기간:** 2026-08-04

#### 문제

첫 화면에서 25개 오디오와 8개 정보 패널이 함께 준비됐습니다.<br/>
Tailwind Play CDN, Framer Motion, 화면 밖 월드 구역과 참조되지 않는 대형 음원도 초기 비용과 배포물에 남아 있었습니다.

<br />

#### 변경

- 8개 정보 패널과 PortfolioViewer를 `React.lazy` 청크로 분리
- 첫 화면 오디오 요청 제거
- 이동·전투·포트폴리오 음원 준비 시점 분리
- Tailwind Play CDN·Framer Motion을 프로젝트 CSS·CSS 애니메이션으로 대체
- 북쪽 호수, 남쪽 절벽·폭포 구역의 화면 밖 렌더 제외
- BGM·영상 재인코딩
- 참조되지 않는 M4A 6개 제거

<br />

#### 과거 빌드 재측정과 파일 확인

| 지표 | 전 | 후 |
| --- | ---: | ---: |
| 첫 화면 오디오 요청 대상 · Git blob 합 | 25개 · 2,149,367B | 0 |
| 사용자 진입 직후 필수 오디오 · Git blob 합 | 25개 · 2,149,367B | 12개 · 516,145B |
| 4차 당시 메인 JavaScript gzip | 214,803B | 113,906B · -47.0% |
| 활성 BGM 2개 + 영상 · Git blob 합 | 6,603,424B | 3,394,970B · -48.6% |
| 참조되지 않는 M4A 6개 · Git blob 합 | 164,354,576B | 제거 |

메인 JavaScript는 2026년 8월 25일 내부 리비전 `2328a82^`와 `2328a82`를 같은 Node·Vite 환경에서 다시 빌드한 뒤 `zlib.gzipSync`로 확인했습니다.<br/>
당시 작업 기록에는 수정 후가 `114,888B`로 적혀 있었지만 다시 확인되지 않아 `113,906B`로 바로잡았습니다.<br/>
현재 운영 번들의 크기를 뜻하지 않습니다.

재인코딩한 물결 영상은 재생 시간·해상도·프레임률을 유지했습니다.<br/>
화면 품질 비교의 산출 로그는 남아 있지 않아 SSIM·PSNR을 검증 근거로 사용하지 않습니다.

당시 TypeScript 정적 회귀 묶음 31개는 26개가 통과하고 기존 좌표·문자열 기대값 5개가 일치하지 않았습니다.<br/>
이 묶음과 별도로 실행한 NPC 검사에서도 기대식 불일치 1개가 남았습니다.<br/>
성능 변경과 관련된 타입·빌드·사운드·레이아웃·컬링 검사는 통과했습니다.

### 5차 — 시작 화면과 회전 대기 뒤 숨은 작업

**기간:** 2026-08-10

#### 문제

모바일 시작 화면과 가로 회전 안내가 월드를 완전히 덮고 있어도 GameWorld는 계속 update/draw를 수행했습니다.<br/>
첫 입력 전 진입 BGM과 효과음 준비도 시작됐습니다.<br/>
`포트폴리오 바로 보기` 뒤에는 시작 오버레이가 남았습니다.

<br />

#### 변경

- GameWorld는 아트와 최초 프레임만 준비한 뒤 실제 진입까지 update/draw 중단
- coarse pointer 환경의 진입 음악·필수 SFX를 첫 입력까지 유예
- 포트폴리오 본문에서 숨은 WelcomeOverlay와 전역 키 입력 제거

<br />

#### 전후 실측

동일 `390×844`, DPR 3, `prefers-reduced-motion: reduce` Chromium에서 수정 전·후 production build를 각각 3회 측정한 중앙값입니다.

표의 Script와 Task는 당시 브라우저 성능 계측에서 해당 구간에 기록한 누적 시간입니다.<br/>
원시 trace와 추출 명령은 남아 있지 않아 공개 저장소에서 같은 값을 다시 계산할 수 없습니다.

첫 입력 전 동일 출처 전송은 당시 바이트 집계값만 남아 있고 Resource Timing의 어떤 필드를 합산했는지는 보존되지 않았습니다.

## 4. iPhone Safari: viewport, font swap, raster를 분리하기

### 관찰

특정 iPhone 17 Pro Safari에서 다음 증상을 확인했습니다.

1. 주소창이 펼쳐진 가로 화면에서 메뉴가 아래로 밀림
2. 세로 홈 `PROJECT`가 처음 다른 글꼴로 보인 뒤 위치가 바뀜
3. 패널에 안착한 글자가 한 프레임 뒤 다시 흐려짐

세 현상을 하나의 CSS 적용 지연으로 보지 않고 원인을 나눴습니다.

<br />

### 4-1. 동적 viewport

**원인:** CSS가 가정한 390px 높이와 주소창이 펼쳐진 실제 표시 높이가 달랐습니다.

**해결:** `100dvh`와 size container를 사용하고 실제 높이가 340px 이하일 때만 버튼 높이 `52→44px`, 간격 `10→6px`로 압축했습니다.

**검증:** `844×290`에서 document scrollHeight 290px, 두 메뉴 가시성, 44px touch target과 6px 간격을 확인하고 390px 복원 시 원래 규칙으로 돌아오는지 검사했습니다.

<br />

### 4-2. font swap과 우측 정렬

**원인:** Google Fonts의 `display=swap`으로 fallback 글꼴이 Silkscreen으로 교체되며 7글자의 실제 폭이 달라졌습니다.<br/>
우측 정렬이라 오른쪽 끝은 같아도 왼쪽과 중심이 이동했습니다.

**해결:** `PROJECT` 7글자만 포함한 Silkscreen WOFF2 subset을 인라인하고 앱 mount에서 Font Loading API로 선로딩했습니다.<br/>
`font-synthesis: none`으로 가짜 굵기도 막았습니다.

**검증:** 외부 Google Fonts 요청 0, 폰트 준비 뒤 20프레임에서 Range `left/right/width/center` 변화 0px를 확인했습니다.

<br />

### 4-3. WebKit 재래스터링

**원인:** 약 3.175px로 먼저 축소한 글자를 부모에서 약 3.15배 확대하면 계산 크기는 10px이어도 WebKit은 작은 glyph layer를 다시 확대해 흐릴 수 있었습니다.<br/>
완료된 animation을 정적 transform으로 교체할 때 합성 layer가 재생성되는 한 프레임도 있었습니다.

**해결:** 패널 상태에서는 `PROJECT`를 10px 원본 크기로 직접 렌더하고 패널이 닫힐 때까지 완료된 focus-in 행렬과 합성 상태를 유지했습니다.

**검증:** 완료 120ms 뒤 이어지는 8프레임에서 패널 Y, 브랜드 중심, DOMADO·PROJECT glyph 좌표 변화 허용치를 0.01px 이하로 검사했습니다.<br/>
360×800, 390×844, 412×915에서도 중앙 정렬과 우측 끝을 확인했습니다.

<br />

### 한계

증상 발견과 육안 확인에는 실제 iPhone을 사용했지만 정밀 좌표 자동화는 Chromium 기반입니다.<br/>

- 매 프레임 새 방향을 골라 우회 방향을 유지하지 못함

<br />

### 변경

- 플레이어 문 통로는 유지하고 NPC만 피하는 영역을 추가했습니다.
- 가로 이동이 막히면 상·하, 세로 이동이 막히면 좌·우를 먼저 검사합니다.
- 선택한 우회 방향을 `0.8~1.3초` 유지합니다.
- HMR로 이미 끼어 있던 NPC를 정상 좌표로 복구하는 경로도 처리했습니다.

<br />

### 검증

수정 전 실패하는 재현 검사를 먼저 만들고 우회 후 통과하는지 확인했습니다.<br/>
플레이어의 문 통로, 다른 주민 이동, 브라우저 콘솔도 함께 확인했습니다.

<br />

### 의미

NPC 끼임은 **기하와 의사결정 정책의 조합** 때문에 생겼습니다.<br/>
좌표 한 곳만 옮기지 않고 월드가 커져도 같은 끼임이 반복되지 않도록 이동 정책을 바꿨습니다.

## 7. Gemini를 브라우저 기능에서 서버리스 계약으로 바꾸기

### 문제

초기 버전은 브라우저에서 Gemini SDK와 `VITE_GEMINI_API_KEY`를 사용했습니다.<br/>
Vite의 `VITE_*` 값은 번들에 포함되므로 비밀을 보관할 수 없습니다.<br/>
서버리스로 옮긴 초기 버전도 공급자 실패를 하나의 502로만 표현했습니다.

<br />

### 변경

Vercel Serverless Function으로 호출을 옮기고 다음 계약을 구현했습니다.

| 경계 | 계약 |
| --- | --- |
| method | `POST`만 허용, 그 외 405와 `Allow: POST` |
| origin | Origin이 있는 요청만 forwarded host/host와 비교 |
| body | Content-Length와 raw stream 문자열 길이 상한 4,096 |
| prompt | trim 후 필수, 최대 500자 |
| history | 최대 4개, `user/npc` 역할, 메시지 최대 600자 |
| secret | API key와 system instruction은 서버에서만 사용 |
| cache | JSON 응답 `Cache-Control: no-store` |
| provider | 429→rate limited, 404→model unavailable, 그 외→upstream failure |

클라이언트는 최근 대화만 보내고 API 오류를 연결 중·정상·제한·오프라인 상태로 바꿉니다.

<br />

### 검증

성공, method 오류, 외부 origin, 빈·긴 질문, 잘못된 history, key 미설정, 일반 upstream 실패, 429, 404를 서버 단위 검사로 확인했습니다.<br/>
개발·preview 서버도 같은 handler를 사용하도록 구성했습니다.

<br />

### 한계

- Origin이 없는 요청은 현재 허용합니다.
- 프레임워크가 미리 파싱한 `request.body` 객체의 전체 크기는 다시 계산하지 않습니다.
- 애플리케이션 rate limit은 없습니다.
- Supabase RLS/schema/migration과 배포 IaC는 비공개 구현 저장소에도 없습니다.
- 모델 이름과 공급자 정책은 바뀔 수 있어 특정 버전을 성과로 삼지 않습니다.

<br />

## 8. 라이선스 에셋을 런타임 월드로 통합하기

<br />

### 배포 경계 문제

작업용 원본이 `public/`에 남으면 코드에서 쓰지 않아도 배포될 수 있습니다.<br/>
저장소를 공개할 때 원본까지 재배포할 위험도 생깁니다.<br/>
실행 참조와 allowlist를 감사했습니다.

| 항목 | 정리 전 | 정리 후 |
| --- | ---: | ---: |
| `public/assets` 추적 파일 | 1,008 | 126 |
| `public` | 약 29MB | 약 16MB |
| `dist` | 약 30MB | 약 17MB |

미사용 원본과 편집 파일은 Git·배포 경로 밖으로 옮겼습니다.<br/>
기대 파일 126개와 실제 추적 파일 126개, 누락·초과 0을 확인했습니다.

<br />

### 한계

- 실행에 필요한 픽셀 자산은 브라우저에 전달되므로 다운로드 자체를 막을 수 없습니다.
- 비공개 구현 저장소의 HEAD에서 삭제해도 과거 Git 객체는 남습니다.
- 공개 SVG에는 원본 sprite sheet나 편집용 에셋을 넣지 않았습니다.<br/>
  모션에 필요한 이미지는 완성 화면을 평면화한 캡처만 사용했습니다.
- README의 게임 화면 이미지는 프로젝트 화면을 평면화·축소한 자료이며 원본 재배포 권리를 부여하지 않습니다.
