# DOMADO 개발 연대기

[← README](../README.md) · [엔지니어링 사례](./engineering-cases.md) · [DOMADO 플레이](https://domado.me)

DOMADO는 2025년 11월 레트로 OS형 포트폴리오로 시작했습니다.<br/>
2026년 7월 기존 UI를 걷어 내고 탐색 가능한 Canvas 월드로 전환한 뒤, 모바일 입력과 게임 시스템, 포트폴리오 뷰어, 서버리스 연동, 성능과 Safari 문제를 차례로 다뤘습니다.

이 문서는 다음 단계로 넘어간 이유를 개발 전환점 9개로 나눠 기록합니다.<br/>
기간·diff·자산 수는 비공개 구현 이력과 당시 작업 기록을 기준으로 합니다.

<br />
<br />

## 0. 레트로 OS형 포트폴리오

**기간:** 2025-11-26 ~ 2026-02-14

### 출발점

첫 버전은 사용자가 데스크톱 OS를 조작하듯 포트폴리오를 탐색하는 React 애플리케이션이었습니다.

- BIOS 스타일 부팅 시퀀스와 Web Audio 효과
- 드래그·최소화·포커스·z-index를 갖는 Window Manager
- About·Projects·Skills를 비롯한 6개 앱
- Supabase 방명록, EmailJS 연락 폼, Gemini 안내 터미널

<br />

### 남은 자산과 드러난 한계

프로젝트 데이터와 외부 서비스 연동은 이후 게임 패널의 기반이 됐습니다.<br/>
다만 방문자는 여전히 아이콘을 누르고 목록을 읽었고 인터랙션과 포트폴리오 내용도 충분히 연결되지 않았습니다.<br/>
Gemini 키를 브라우저 `VITE_*` 환경 변수에서 읽는 문제까지 남아 있어 기능 추가보다 탐색 방식 자체를 바꾸기로 했습니다.

## 1. 레트로 OS를 버리고 게임 월드로 전환

**기간:** 2026-07-09 ~ 07-10

### 무엇을 남기고 버렸나

| 유지 | 폐기 | 새로 설계 |
| --- | --- | --- |
| 소개·프로젝트·기술 데이터, Supabase, EmailJS, AI 안내 | Window, Taskbar, BootScreen, Paint, Music Player, ControlPanel과 CRT 셸 | GameWorld, 월드 오브젝트, 공용 패널, QuickMenu, 모바일 홈 |

콘텐츠와 검증된 연동은 보존하고 정보 탐색을 방해하는 OS 셸은 걷어 냈습니다.<br/>
캐릭터만 덧붙이지 않고 제품 구조를 다시 만들면서 41개 파일에서 `+2,038 / -3,147`줄이 바뀌었습니다.

<br />

### 처음 정한 구조 원칙

- 콘텐츠와 패널 연결 규칙을 공용 데이터로 모읍니다.
- 고빈도 게임 상태와 저빈도 UI 상태의 소유권을 나눕니다.
- 데스크톱 게임과 모바일 정보 접근을 별도 사용자 흐름으로 설계합니다.

처음에는 DOM/CSS 방과 CSS 캐릭터도 검토했습니다.<br/>
별도 게임 엔진의 추상화·유지보수 비용을 늘리지 않은 채 React·TypeScript·Canvas API 안에서 필요한 범위를 직접 통제하는 쪽을 선택했습니다.

## 2. 걸을 수 있는 화면을 하나의 마을로 만들기

**기간:** 2026-07-11 ~ 07-13

### 기능을 연결한 순서

기술 텃밭과 주민을 먼저 배치하고 시장 상인의 선택지와 검 획득, 걷기·공격 효과음을 연결했습니다.<br/>
폭포·절벽·동굴·사다리와 전초기지 전투를 더한 뒤 분수·광장·랜턴·경고판으로 각 구역을 하나의 동선으로 묶었습니다.

<br />

### 폭포를 반복해서 고친 이유

폭포는 미관만의 문제가 아니었습니다.<br/>
물 타일의 반복, 절벽 가장자리, 접근 가능한 길, 동굴 입구, 사다리 진입점과 충돌 영역이 서로 맞아야 했습니다.<br/>
한쪽을 옮기면 다른 규칙도 함께 바뀌었습니다.

보이는 지형과 발밑 충돌을 구분하고 통과해야 할 문과 다리는 큰 collider에서 명시적으로 뺐습니다.<br/>
장식 좌표·깊이 정렬·상호작용 범위는 한곳에서 관리했습니다.<br/>
이후 농장·시장·대장간 구역에서도 시각·동선·충돌을 함께 맞췄습니다.

## 3. 데스크톱 월드를 모바일 제품으로 바꾸기

**기간:** 2026-07-13 ~ 07-20

### 반응형 CSS만으로 풀 수 없었던 문제

`672×448` 월드를 작은 화면에 그대로 축소하면 캐릭터와 대상이 너무 작아졌습니다.<br/>
반대로 세로 화면에 가상 조이스틱을 억지로 넣으면 정보 열람도 게임 조작도 불편했습니다.<br/>
월드를 두 벌로 만들면 시각·충돌·동선을 함께 유지해야 하는 비용이 생겼습니다.

<br />

### 화면과 입력 정책

- 모바일 세로: 8개 카드 중심의 정보 탐색
- 모바일 가로: 폭 전체를 유지하고 세로축을 추적하는 카메라
- 입력: 플로팅 조이스틱과 상황별 단일 액션 버튼
- 보조: 전체 지도, 현재 위치, 전체화면 복귀, safe-area
- 실패 허용: fullscreen·orientation lock이 거절돼도 수동 회전 흐름 유지

고주사율 기기에서는 평균 FPS보다 흔들리는 프레임 간격이 먼저 눈에 띄었습니다.<br/>
RAF 간격·실행 기한·누락된 RAF 호출을 보정하고 화면 밖 렌더 제외·입력 병합·배열 재사용으로 모바일 프레임 예산을 관리했습니다.<br/>
수치와 조건은 [성능 사례](./engineering-cases.md#1-일곱-차례의-성능-개선)에 모았습니다.

<br />

### 살아 있는 월드로 확장

모바일 기반을 잡은 뒤 현실 3분 주기의 낮·해질녘·밤, 해·달 HUD, 지도, 메인 퀘스트, 작물 성장, 주민·낚시꾼·농부 상태를 추가했습니다.<br/>
북쪽 마을과 농장은 세 가지 레이아웃 대안을 비교한 뒤 최종 배치를 선택했고 단구·계단·울타리·농지 충돌도 함께 점검했습니다.

<br />

## 4. 기록 보관소와 첫 서버 경계

**기간:** 2026-07-29 ~ 08-02

### 마을 안과 밖에서 같은 기록 읽기

마을 안에 포트폴리오 기록 보관소를 연결했고 게임을 하지 않아도 시작 화면에서 같은 6페이지 포트폴리오로 바로 들어갈 수 있게 했습니다.

- 첫 페이지 물결 영상과 6페이지 기록
- 이전/다음, 스와이프, 드래그, 핀치 확대, 더블 탭 초기화
- 게임 안 보관소와 시작 화면의 `포트폴리오 바로 보기`
- 첫 페이지와 물결 영상은 전환 중 준비하고 후속 페이지는 본문 표시 뒤 유휴 시간에 순차 준비

6MB가 넘는 영상과 여러 페이지를 동시에 준비하면서 자원 경쟁이 생겼습니다.<br/>
파일 크기를 줄이는 동시에 준비 순서도 나눴습니다.

<br />

### 첫 방문 가이드

조작 설명을 한 장에 몰아넣지 않고 실제 대상과 지도 위치를 연결한 단계형 가이드로 만들었습니다.<br/>
데스크톱과 터치 환경을 분리하고 건너뛰기·다시 보기·focus trap·Escape 복귀를 추가했습니다.

<br />

### 브라우저 키를 서버로 이동

Gemini SDK와 키를 브라우저에서 직접 사용하던 구조를 Vercel Serverless Function으로 옮겼습니다.<br/>
키와 시스템 지식은 서버에 두고 서버 경계에서 method·origin·본문·prompt·history를 검증하도록 했습니다.<br/>
실제 공급자 오류를 구분하는 작업은 이후 안정화 단계에서 이어졌습니다.

## 5. 첫 화면과 자원 수명 주기 재설계

**기간:** 2026-08-04 ~ 08-10

### 첫 화면이 게임 전체를 부담하던 문제

월드와 패널이 풍부해질수록 첫 화면에서 오디오, 정보 패널 코드, 대형 미디어와 화면 밖 구역이 함께 준비됐습니다.<br/>
기능은 유지하면서 자원의 준비 시점을 나눴습니다.

- 정보 패널과 PortfolioViewer 코드 분할
- Tailwind Play CDN·Framer Motion을 프로젝트 CSS·CSS 애니메이션으로 대체
- 이동·전투·포트폴리오 음원의 준비 시점 분리
- 호수·절벽·폭포 구역의 화면 밖 렌더 제외
- BGM·영상 재인코딩과 미참조 대형 음원 제거

<br />

### 시작 화면에 사용 목적 반영

- 데스크톱: 마을 탐험하기 / 포트폴리오 바로 보기
- 모바일 세로: 마을 탐험하기 / 포트폴리오 바로 보기 / 카드로 빠르게 보기
- 모바일 가로: 마을 탐험하기 / 포트폴리오 바로 보기

목적지마다 전용 전환을 두고 음악 수명 주기를 따로 관리합니다.<br/>
로딩 화면은 합성한 네트워크 퍼센트나 시스템 로그 대신 실제 화면 전환 상태만 보여 주도록 정했습니다.

<br />

### 보이지 않는 월드 중단

모바일 시작 화면과 회전 안내가 화면을 완전히 덮어도 GameWorld는 계속 update/draw했습니다.<br/>
아트와 최초 프레임만 준비한 뒤 실제 진입까지 게임 루프를 멈추고 coarse pointer 환경의 오디오 준비도 첫 입력까지 미뤘습니다.

## 6. 런타임과 정보 패널 마감

**기간:** 2026-08-11 ~ 08-17

### 멈춘 게임이 계속 그려지던 문제

패널이나 퀘스트로 게임이 일시정지돼도 완성된 월드를 매 RAF 다시 그렸습니다.<br/>
패널에 들어갈 때 한 프레임을 저장해 재사용했습니다.<br/>
큰 초기 상태·정적 sprite·crop 결과도 한 번만 만들도록 바꿨습니다.<br/>
모바일은 GPU Canvas 유실을 피하기 위해 저장본 한 장을 매 RAF blit하는 예외를 뒀습니다.

<br />

### 정보와 월드의 의미 연결

정보 패널을 데스크톱·모바일 세로·모바일 가로에서 함께 쓸 수 있게 정리하고 풍차와 프로젝트처럼 월드 오브젝트와 패널의 의미를 맞췄습니다.

<br />

### 실제 오류를 보고 API 계약 보강

서버리스 이전 뒤 실제 `429`와 `404`를 겪었습니다.<br/>
모든 외부 실패를 하나의 `502`로 보내는 대신 제한 상태, 모델 사용 불가, 그 밖의 upstream 실패를 나눴고 클라이언트의 `ONLINE / LIMITED / OFFLINE` 상태까지 연결했습니다.

## 7. iPhone Safari와 배포 경계 마감

**기간:** 2026-08-20 ~ 08-21

### 하나처럼 보인 세 가지 Safari 문제

1. 주소창이 펼쳐지며 실제 가로 viewport 높이가 짧아짐
2. Google Fonts fallback이 Silkscreen으로 바뀌며 글자 폭과 정렬이 움직임
3. 작은 글리프를 축소 후 확대하면서 WebKit이 흐린 layer를 다시 합성함

각 원인에 맞춰 `100dvh`·size container와 7글자 WOFF2 인라인 선로딩을 적용했습니다.<br/>
10px 원본으로 렌더하고 focus-in이 완료된 뒤에도 변환 행렬·합성 상태를 유지했습니다.<br/>
증상은 실제 iPhone에서 찾았고 좌표·프레임 회귀는 Chromium으로 보완했습니다.<br/>
조건과 한계는 [Safari 사례](./engineering-cases.md#4-iphone-safari-viewport-font-swap-raster를-분리하기)에 적었습니다.

<br />

### 전체화면과 user activation

전체화면 요청을 비동기 오디오 준비 뒤에 실행하면 사용자 활성화가 사라질 수 있었습니다.<br/>
버튼 이벤트 안에서 fullscreen을 먼저 요청하도록 순서를 바꿨습니다.<br/>
요청이 실패해도 레이아웃과 수동 회전 흐름은 유지됩니다.

<br />

### 유료 에셋의 배포 경계

실행에 필요한 자산과 작업용 원본이 같은 `public/`에 있으면 사용하지 않는 파일도 배포됩니다.<br/>
저장소를 공개할 때 원본까지 재배포할 위험도 생깁니다.<br/>
실제 참조와 allowlist를 감사해 추적 자산을 `1,008개→126개`로 줄였고 미사용 원본·편집 파일은 Git과 배포 경로 밖으로 옮겼습니다.

실행에 필요한 픽셀 이미지는 브라우저로 전달되므로 다운로드 자체를 막을 수 없습니다.<br/>
삭제 전 Git 객체에도 원본이 남습니다.<br/>
이 때문에 구현 저장소의 과거 이력과 공개 가능한 문서를 분리해 관리하기로 했습니다.

## 8. 첫 화면을 게임 준비가 아닌 목적 선택 화면으로 바꾸기

**기간:** 2026-08-25

### 화면은 빨리 보였지만 메인 스레드는 바빴습니다

시작 화면은 빠르게 나타났지만 뒤에서 즉시 마운트된 GameWorld가 픽셀 아트 로드와 Canvas 합성을 시작했습니다.<br/>
프로파일과 로컬 비교에서 이 초기화가 메인 스레드를 오래 점유하는 원인으로 드러났습니다.

<br />

### 선택한 경로에 필요한 작업만 시작

- 첫 화면에서는 GameWorld를 마운트하지 않고 `마을 탐험하기`를 선택한 뒤 전환 화면 안에서 월드를 준비합니다.
- `포트폴리오 바로 보기`와 모바일 세로의 `카드로 빠르게 보기`는 게임 초기화를 건너뜁니다.
- 시작 화면용 글꼴 서브셋을 분리하고 공용 월드 SVG의 브라우저 전송량을 `334,820→184,596B`로 줄였습니다.

수정 직전 `695c3db`와 수정 후 `db6bd2b`의 프로덕션 빌드를 같은 URL과 모바일 Lighthouse 환경에서 각각 5회 측정했습니다.<br/>
중앙값은 성능 점수 `75→88`, LCP `6.92→3.46초`, 총 전송량 `1,606,640→433,644B`였습니다.<br/>
FCP는 `2.10→2.40초`로 느려졌고 TBT는 전후 모두 `0ms`였습니다.<br/>
LCP와 전송량은 줄었지만 FCP와 수정 후 LCP는 더 개선해야 합니다.<br/>
측정 조건은 [7차 성능 사례](./engineering-cases.md#7차--시작-화면의-네트워크와-메인-스레드)에 적었습니다.

첫 화면은 게임을 준비하는 곳이 아니라, **방문자가 목적을 고르는 곳**이 됐습니다.
